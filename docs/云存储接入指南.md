# 菜品图云存储接入指南（配图全量化方案）

> 适用前提：A 侧会把 419 道菜逐步补到全量配图。
> 结论：**走微信云存储，不走分包**。真正原因不是容量，而是三条硬规则叠加：
> ① tabBar 页（首页/菜单/我的）必须在主包；② 主包不能引用分包里的图片资源；
> ③ 主包上限 2MB。首页/菜单都要显示菜品图 → 图必须跟 tabBar 页进主包 →
> 419 张约 16MB 塞不进 2MB。**所以「菜品图全量 + 首屏有食欲」只能走网络图**，
> 云存储（cloud:// 免备案免域名）是网络图里最干净的方案。
> 本指南配套代码已就绪（`utils/dishImages.js` 云优先、本地兜底），前端无需再改结构。

---

## 一、为什么是云存储，顺带解决域名合规

| 顾虑 | 云存储（微信云开发）如何化解 |
|---|---|
| 域名备案 | **不需要**。图片用 `cloud://` fileID，是微信内部协议，不经过 HTTP 域名 |
| downloadFile 合法域名 | **不用配**。`cloud://` 不占用合法域名列表 |
| 包体 | 图片全在云端，主包只留代码，可瘦回 ~0.9MB |
| 离线 | 首次加载需联网，之后走微信客户端缓存 |
| 存储容量 | 419 张 × 约 40KB ≈ 17MB，远低于 2GB 免费/套餐配额 |

### 成本时间线（2025–2026 现行政策，务必看）

「所有用户可读」这个**权限设置本身不收费**，收的是云开发**环境套餐**：

| 阶段 | 费用 |
|---|---|
| 开发 / 调试 / 比赛评审期 | **免费**（新用户免费环境 40,000 资源点/月，体验 6 个月；或免费体验版 3,000 点/月） |
| 小程序**正式发布上线**后 | 免费环境到期变更为上线后**第 15 天**，长期用须转付费 **19.9 元/月**（长期 5 折，原价 39） |

**结论**：整个开发 + 比赛评审阶段**一分钱不花**；只有决定「正式发布并长期运营」才产生
19.9 元/月。若届时不想付费，把 `IMAGE_ON_CLOUD` 改回 `false`、图放回主包即可退回零成本方案。

> 备选：若团队坚持自建图床（腾讯 COS 等），则必须 ① 域名 ICP 备案 ② HTTPS
> ③ 把域名加进小程序后台 downloadFile 合法域名。比云开发多三步合规，不推荐本期走。

## 二、一次性准备（约 10 分钟，需 AppID 管理员操作）

1. **开通云开发**：微信开发者工具 → 顶部「云开发」→ 开通 → 创建环境（如 `prod-xxx`）。
2. **建目录**：云开发控制台 → 「存储」→ 新建文件夹 `dishes/`。
3. **设权限**：存储 → 权限设置 → 选「所有用户可读，仅创建者可写」（前端只读图）。
4. **拿到 fileID 前缀**：随便传一张图，复制它的 fileID，形如
   `cloud://prod-xxx.7072-prod-xxx-1300000000/dishes/baiqieji.jpg`
   把**到文件名前为止**的前缀记下：
   `cloud://prod-xxx.7072-prod-xxx-1300000000/dishes/`

---

## 三、上传图片（两种方式，按量级选）

### 小批量（< 50 张，推荐起步用）
云开发控制台 → 存储 → `dishes/` → 直接**拖拽上传**。文件名保持与映射表一致
（如 `baiqieji.jpg`），无需改任何映射。

### 大批量（A 扩容到几百张时）
用官方命令行 `tcb`（腾讯云开发 CLI）批量传：

```bash
npm i -g @cloudbase/cli
tcb login                      # 扫码授权（需管理员）
# 在 scripts/ 下运行（已备好 upload-to-cloud.js，见下）
node scripts/upload-to-cloud.js <环境ID> <本地图片目录>
```

脚本会遍历目录、逐张上传到 `dishes/`、并打印 fileID 清单供核对。

## 四、切流到云（改两行）

打开 `miniprogram/utils/dishImages.js`：

```js
const IMAGE_ON_CLOUD = true;                                   // ① 置 true
const IMAGE_CLOUD_BASE = 'cloud://prod-xxx.7072-.../dishes/'; // ② 填第二步记下的前缀
```

- 映射表 `DISH_IMAGES` 里仍是文件名（`baiqieji.jpg`）→ 自动拼到云前缀。
- **A 扩容的新菜**：直接在映射表填完整云地址（`cloud://.../新菜.jpg`），
  代码识别到 `cloud://` 开头就直接用，与本地旧菜混排无冲突。

## 五、验证与瘦身

1. 开发者工具编译，进首页/菜单/详情，确认菜品图正常显示（云图）。
2. 确认无误后，删除 `miniprogram/images/dishes/` 整个目录 → 主包立刻瘦约 1.1MB。
3. 重新上传代码。此后图片增删全在云控制台操作，不动代码、不动包。

> 节气海报（`images/posters/`，24 张固定 388KB）不会扩容，**留在主包**即可，不必上云。

## 六、A 侧扩容配图的标准工作流

1. A 把新风味卡导出为「裁掉文字区的照片带」（顶对齐 44%，1.6:1，640px，JPEG q68）。
2. 命名用菜名拼音（与 `DISH_IMAGES` 键对应）。
3. 上传到云 `dishes/`。
4. 在 `dishImages.js` 的 `DISH_IMAGES` 或 `ALIAS` 加一行映射。
5. 前端 `sanitizeRecipe` 自动挂图，全端生效，无需发版（若映射走云地址，
   连这行都不改——但建议仍登记进映射表，便于核对哪些菜已配图）。

## 七、常见问题

- **图打不开 / 403**：存储权限没设「所有用户可读」。回第二步。
- **开发者工具提示域名**：说明误用了 `https://` 地址而非 `cloud://`。换回 fileID。
- **想退回本地**：`IMAGE_ON_CLOUD` 改回 `false`，把 `images/dishes/` 放回主包即可。
- **要付费吗**：权限设置免费；开发评审期环境免费；只有正式发布并长期运营才 19.9 元/月（见第一节时间线）。
- **额度不够**：云开发控制台可随时升配；前期免费额度足够覆盖课程/比赛量级。

---

## 八、零成本备选（若一分预算都没有）

若团队确认零预算、也不要求全量配图，可以**完全不上云**：
维持现状——主包只放经典菜图，其余 413 道用 dishMedia 的「风味签」兜底
（暖色渐变 + 斜纹 + 菜系水印 + 朱砂印章，无图也像设计，这是组件的设计初衷）。
`IMAGE_ON_CLOUD` 保持 `false` 即可，代码零改动。代价是放弃「全量配图」。
两条路随时可切，代码已留后门。
